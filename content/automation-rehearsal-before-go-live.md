# ก่อนเปิด Automation จริง: คู่มือซ้อม 3 รอบ ป้องกันส่งซ้ำ ข้อมูลผิด และสิทธิ์เกิน

ระบบอัตโนมัติที่ทำงานตรงเวลายังไม่ถือว่า “พร้อมใช้จริง” หากเราไม่รู้ว่าจะเกิดอะไรเมื่อข้อมูลหาย ปลายทางตอบช้า หรือคำสั่งเดิมถูกรันซ้ำ ความเสียหายมักไม่ได้มาจากระบบหยุดทำงานเพียงอย่างเดียว แต่อาจเป็นอีเมลซ้ำ โพสต์ผิดวัน ใช้ไฟล์เก่า หรือทำงานเกินสิทธิ์ที่ตั้งใจไว้

คู่มือนี้ใช้ได้กับรายงาน การเผยแพร่บทความ การแจ้งเตือน และงานหลังบ้านที่มี AI เป้าหมายคือให้ตอบได้ว่า ระบบรับอะไร ส่งอะไร หยุดตรงไหน และตรวจความสำเร็จจากหลักฐานใด

## โจทย์จริง: รายงาน 18:30 ที่ห้ามส่งผิดหรือส่งซ้ำ

สมมติว่าทีมทำรายงานทุกวันเวลา 18:30 จากไฟล์ที่อัปเดตระหว่างวัน ระบบอ่านข้อมูล ร่างสรุป บันทึกไฟล์ และแจ้งผู้รับหนึ่งคน

ข้อจำกัดคือ ถ้าไฟล์ยังไม่อัปเดตต้องไม่สร้างตัวเลขแทน ถ้ารันซ้ำต้องไม่ส่งซ้ำ และข้อมูลส่วนบุคคลต้องไม่หลุด งานสำเร็จเมื่อไฟล์สุดท้ายเปิดได้และมีหลักฐานจากปลายทาง ไม่ใช่เพียงโปรแกรมจบโดยไม่มี error

ก่อนซ้อม ให้เขียน Automation Contract ระบุ Input, Trigger, Steps, Output, สิทธิ์ เงื่อนไขหยุด หลักฐานสำเร็จ และผู้รับผิดชอบ ช่องที่ยังเขียนไม่ได้คือความกำกวมที่ต้องแก้ก่อนเปิดจริง

## รอบที่ 1: ซ้อมด้วยข้อมูลจำลองและปิดการส่งออก

รอบแรกคือ Dry Run ใช้ข้อมูลจำลองที่ไม่มีความลับ และเปลี่ยนปลายทางเป็นพื้นที่ทดสอบ ระบบแสดงสิ่งที่ “ตั้งใจจะทำ” แต่ไม่ส่งอีเมล ไม่เผยแพร่ ไม่ชำระเงิน และไม่แก้ข้อมูลจริง

ใช้ไฟล์จำลองสามแถวและเว้นค่าหนึ่งช่อง เพื่อดูว่าระบบระบุ “ข้อมูลไม่ครบ” แทนการเติมตัวเลข ตรวจชื่อไฟล์ วันที่ เขตเวลา ลำดับขั้น และการแยกข้อเท็จจริงจากข้อสังเกต

ผลลัพธ์คือ Preview บันทึกขั้นตอน และสถานะ “ยังไม่ส่ง” หากเข้าถึงปลายทางจริงโดยไม่จำเป็น ให้ลดสิทธิ์ก่อนซ้อมต่อ

## รอบที่ 2: จงใจทำให้พังและดูว่าระบบหยุดอย่างไร

รอบสองคือ Failure Drill อย่างน้อยสามแบบ: ไฟล์หาย ข้อมูลเก่า และปลายทางไม่ตอบ อาจเพิ่มรูปแบบข้อมูลผิดหรือบริการภายนอกคืนผลไม่ครบ

ระบบต้องล้มแบบอธิบายได้: ข้อมูลหายให้หยุดก่อนร่าง ข้อมูลเก่าให้เตือนแทนการอ้างว่าล่าสุด ปลายทางช้าให้ retry อย่างจำกัดแล้วแจ้งผู้รับผิดชอบ ห้ามวนไม่สิ้นสุดหรือเปลี่ยนแหล่งข้อมูลโดยเงียบ ๆ

บันทึกสี่ช่อง: สิ่งที่จำลอง / จุดหยุด / ข้อความที่ผู้รับเห็น / วิธีนำระบบกลับมา ตัวอย่าง: “ลบไฟล์ → หยุดก่อนร่าง → แจ้งว่ายังไม่มีการส่ง → วางไฟล์ที่ตรวจแล้วและรันด้วยรหัสงานเดิม”

## รอบที่ 3: ทดสอบการรันซ้ำ สิทธิ์ และหลักฐานปลายทาง

รอบสุดท้ายเชื่อมเฉพาะ Draft, Staging หรือผู้รับทดสอบ รันคำสั่งสองครั้งด้วย Job ID เดียวกัน ผลที่ถูกต้องคือพบงานเดิมและไม่ส่งซ้ำ หลักการนี้เรียกว่า Idempotency

ตรวจ Least Privilege: งานอ่านไฟล์ไม่ควรลบ งานร่างไม่ควรเผยแพร่เอง และขั้นส่งออกควรรับเฉพาะฉบับที่อนุมัติแล้ว หากใช้ AI ให้ส่งเท่าที่จำเป็น ปกปิดข้อมูลส่วนบุคคล และไม่ใส่รหัสผ่าน Token หรือเอกสารลับใน Prompt

ตรวจปลายทางทดสอบว่าไฟล์เปิดได้ URL ตอบสนอง เนื้อหาตรง ภาพครบ และ metadata ถูกต้อง เก็บเวลา Job ID หรือ checksum เท่าที่จำเป็น โดยไม่บันทึกความลับลง log

## Prompt ให้ AI ช่วยออกแบบการซ้อม

> คุณเป็นผู้ช่วยวิเคราะห์ความเสี่ยงของ Automation จงใช้เฉพาะรายละเอียดที่ให้ ห้ามสมมติฟีเจอร์ ราคา หรือสิทธิ์ของแพลตฟอร์ม จัดผลเป็น 5 ส่วน: 1) ขั้นตอนและผลข้างเคียง 2) แผน Dry Run ที่ไม่ส่งออกจริง 3) Failure Drill อย่างน้อย 3 กรณี 4) วิธีป้องกันงานซ้ำและจำกัดสิทธิ์ 5) หลักฐานที่ต้องตรวจจากปลายทาง หากข้อมูลไม่พอให้เขียนคำถาม ห้ามสรุปว่าพร้อมใช้งานแทนผู้อนุมัติ
>
> รายละเอียดงาน: [วาง Automation Contract]  
> สิ่งที่ห้ามเกิด: [ระบุความเสียหายที่รับไม่ได้]  
> เครื่องมือและสิทธิ์ที่มี: [ระบุตามจริง]  
> วิธีอนุมัติปัจจุบัน: [ระบุผู้รับผิดชอบ]

ผลลัพธ์ตัวอย่างที่ดีควรชี้ว่า ขั้น “ส่งข้อความ” เป็นผลข้างเคียง จึงต้องแทนด้วย Draft ในรอบแรก เสนอให้ทดสอบไฟล์หาย ข้อมูลเก่า และ timeout พร้อมจุดหยุด ระบุ Job ID สำหรับกันส่งซ้ำ และขอข้อมูลเพิ่มหากยังไม่ทราบว่าปลายทางยืนยันการรับอย่างไร ผลลัพธ์ที่ไม่ควรยอมรับคือคำตอบว่า “ระบบปลอดภัยแล้ว” โดยไม่มีหลักฐาน หรือสร้างชื่อคำสั่งและความสามารถของแพลตฟอร์มขึ้นเอง

## ข้อควรระวังและก้าวแรกวันนี้

การซ้อมสามรอบช่วยเปิดเผยความเสี่ยง แต่ไม่รับประกันว่าระบบจะไม่ผิดพลาด ต้องทบทวนใหม่เมื่อเปลี่ยนแหล่งข้อมูล สิทธิ์ โมเดล AI ปลายทาง หรือกฎธุรกิจ งานที่กระทบเงิน สุขภาพ กฎหมาย ความปลอดภัย หรือข้อมูลสำคัญควรมีผู้เชี่ยวชาญและการอนุมัติจากมนุษย์ ไม่ควรเปิดอัตโนมัติเต็มรูปแบบเพียงเพราะผ่านข้อมูลทดสอบ

ก้าวแรกวันนี้คือเลือก Automation เพียงหนึ่งงาน เขียน Rehearsal Card ให้ครบ แล้วทำรอบ Dry Run โดยปิดการส่งออกทั้งหมด หากต้องออกแบบโครงงานก่อน เริ่มจาก [OpenClaw ขั้นกลาง: จากแชตหนึ่งครั้งสู่ Workflow ที่ทำซ้ำได้](/articles/openclaw-intermediate-workflows/) และใช้ [ระบบตรวจคำตอบ AI 3 ชั้น](/articles/ai-output-quality-gate/) เป็น Quality Gate ก่อนอนุมัติ
